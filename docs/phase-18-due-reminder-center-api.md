# فاز ۱۸ — API مرکز یادآوری سررسیدها

## هدف و محدوده

این برش یک خروجی خواندنی و پایدار و رابط عملیاتی برای مرکز یادآوری مدیریت فراهم می‌کند. محاسبه به ساعت سیستم یا حدس timezone وابسته نیست: رابط تاریخ «امروز» تهران و انتهای بازه را صریحاً به‌صورت جلالی ارسال می‌کند. اعلان خودکار و تقویم خارجی در این مرحله نیست.

## قرارداد API

```text
GET /api/v1/due-reminders?today_jalali=1405/06/10&through_jalali=1405/06/17
Authorization: Bearer <admin-token>
```

هر دو تاریخ اجباری، قابل ورود با رقم فارسی/عربی/لاتین و در پاسخ canonical هستند. اگر انتهای بازه پیش از امروز باشد، API با `422` و پیام فارسی درخواست را رد می‌کند.

پاسخ چهار بخش دارد:

- `overdue`: موعدهای پیش از امروز؛
- `today`: موعدهای دقیقاً امروز؛
- `upcoming`: موعدهای پس از امروز تا انتهای بازه، با احتساب روز انتهایی؛
- `totals`: جمع کل سه گروه.

هر گروه علاوه بر `items`، این جمع‌ها را دارد:

- `count` و `total_rial`؛
- `receivable_count` و `receivable_total_rial`؛
- `payable_count` و `payable_total_rial`.

## قرارداد پایدار item

هر ردیف دارای فیلدهای زیر است:

- `kind`: یکی از `ledger_entry` یا `cheque`؛
- `record_id`؛
- `person_id` و نام فعلی شخص در `person_name`؛ برای چک بدون شخص هر دو می‌توانند `null` باشند؛
- `direction`: یکی از `receivable` یا `payable`؛
- `record_type`: برای سند `debit|credit` و برای چک `received|paid`؛
- `amount_rial`: مانده سند (`remaining_rial`) یا کل مبلغ چک؛
- `due_jalali_date` و `status`؛
- `description`؛
- `cheque_number` و `bank_name` که برای سند حساب `null` هستند.

مقادیر enum عمداً canonical و مستقل از زبان نگه داشته شده‌اند تا frontend برچسب فارسی و دسترس‌پذیر مناسب را نمایش دهد.

## قواعد ورود و حذف از یادآوری

سند دفتر حساب فقط وقتی وارد خروجی می‌شود که:

- فعال و باز باشد؛
- مانده مثبت داشته باشد؛
- سررسید صریح و غیرخالی داشته باشد؛
- سررسید آن از `through_jalali` عبور نکرده باشد.

چک فقط وقتی وارد خروجی می‌شود که فعال، `pending` و در بازه باشد. بنابراین سند بدون موعد، سند تسویه/باطل/غیرفعال، چک وصول/پاس/برگشت/ابطال‌شده و موعد پس از انتهای بازه نمایش داده نمی‌شوند.

ترتیب کل داده ابتدا سررسید، سپس `kind` و سپس شناسه است. هر منبع با یک query همراه join شخص خوانده می‌شود؛ در نتیجه نام اشخاص N+1 query ایجاد نمی‌کند و هر رکورد تنها یک‌بار در یکی از سه گروه قرار می‌گیرد.

## آزمون دستی پس از اتصال UI

1. یک سند یا چک معوق، یکی برای امروز و یکی برای انتهای بازه بسازید؛ هر سه باید در گروه درست دیده شوند.
2. مبلغ کل و تفکیک دریافتنی/پرداختنی را با ردیف‌ها تطبیق دهید.
3. یک چک بدون شخص ثبت کنید؛ کارت باید بدون خطا و با برچسب «بدون شخص» نمایش داده شود.
4. یک سند بدون سررسید و یک چک وصول‌شده بسازید؛ هیچ‌کدام نباید در مرکز یادآوری دیده شوند.
5. بازه نامعتبر وارد کنید؛ پیام فارسی نمایش داده شود و فهرست قبلی ناخواسته پاک نشود.
6. همین بررسی را در عرض `390 × 844` انجام دهید؛ کارت‌ها، مبالغ و فیلتر تاریخ نباید هم‌پوشانی یا اسکرول افقی داشته باشند.

## تست خودکار

تست‌ها مرز دقیق گذشته/امروز/روز انتهایی، ترتیب پایدار، چک با شخص nullable، direction/type، جمع گروه و کل، exclusion همه وضعیت‌های نامعتبر، canonical شدن تاریخ فارسی، احراز هویت و بازه نامعتبر را پوشش می‌دهند. آزمون شمارش SQL نیز تأیید می‌کند endpoint با سه statement اجرا می‌شود: یک lookup احراز هویت و دو query join‌شده برای منابع مالی.

نتیجه بازبینی عامل اصلی: مجموعه backend برابر `187 passed` با ۶ هشدار deprecation قدیمی؛ تست اعداد frontend برابر ۳ از ۳ و build production با ۹۷۶ ماژول موفق است.

رابط نهایی شامل افق ۷/۱۴/۳۰ روز، KPI و کارت‌های سه گروه، loading/empty/error/retry، مسیر مستقیم به دفتر شخص یا کارت چک و شمار واقعی داشبورد است. QA تعاملی نهایی دسکتاپ و موبایل در تست پذیرش کاربر باقی می‌ماند.
