# فاز ۳۰ — اجرای زمان‌بندی‌شده و مانیتورپذیر بکاپ

## محدوده تحویل

- یک wrapper مستقل برای اجرای `create → verify → prune` اضافه شد؛ حذف نسخه‌های قدیمی فقط پس از ساخت و اعتبارسنجی موفق نسخه تازه انجام می‌شود.
- مقصد بکاپ و فایل وضعیت اجباری و صریح‌اند تا job به مسیر اتفاقی یا داخل مخزن ننویسد.
- فایل `status.json` به‌صورت اتمیک و با permission محدود، حالت‌های `running`، `success` و `failure` را ثبت می‌کند.
- خروجی شکست فقط نام کلاس خطا را نگه می‌دارد؛ متن exception، مسیر خصوصی، URL یا secret در status و stderr منتشر نمی‌شود.
- مقادیر retention و timeout پیش از ساخت bundle اعتبارسنجی می‌شوند؛ تنظیم نامعتبر هیچ بکاپ اضافه‌ای نمی‌سازد.
- خطاهای پیش‌بینی‌نشده نیز در مرز CLI به exit code یک و وضعیت failure مانیتورپذیر تبدیل می‌شوند.

## حفاظت از داده واقعی

این فاز فقط ابزار و راهنمای اجرا را اضافه می‌کند. Scheduled Task واقعی PythonAnywhere فعال نشده، هیچ bundle جدیدی روی production ساخته یا حذف نشده و هیچ فایل off-host ارسال نشده است. فعال‌سازی production و انتخاب مقصد رمزگذاری‌شده خارج از هاست نیازمند بازبینی و تأیید کاربر است.

## شواهد خودکار

- تست‌های wrapper و هسته bundle: ۱۸ موفق.
- سناریوهای موفقیت، شکست sanitize‌شده، نوشتن اتمیک status، retention پس از موفقیت، عدم prune در شکست، تنظیم retention نامعتبر و Exception پیش‌بینی‌نشده پوشش داده شدند.
- کل backend: ۲۳۵ تست موفق.

## تست دستی کوتاه پس از تأیید برای محیط جدا

1. فرمان مستندشده را با دیتابیس و media آزمایشی اجرا کنید؛ exit code صفر و `status.json` با حالت `success` دیده شود.
2. یک مسیر منبع نامعتبر بدهید؛ exit code یک و فقط `error_code` عمومی در status/log ثبت شود.
3. آخرین bundle را با فرمان verify بررسی و در مسیر موقت restore کنید؛ شمار رکوردها و تصویرهای ارجاع‌شده تطبیق داده شوند.
4. در PythonAnywhere فقط پس از این آزمون‌ها Scheduled Task روزانه فعال شود و زمان آخرین موفقیت پایش شود.

این فاز روی هاست deploy یا فعال نشده و تا بازبینی کاربر فقط در شاخه کاری باقی می‌ماند.
