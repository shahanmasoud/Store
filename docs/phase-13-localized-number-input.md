# فاز ۱۳ — ورودی عددی فارسی و عربی

این فاز لایهٔ دفاعی backend برای پذیرش امن ارقام محلی را اضافه می‌کند. نوع پاسخ API و نوع ستون‌های دیتابیس تغییر نکرده و هیچ migration یا پاک‌سازی خودکار دادهٔ قدیمی انجام نمی‌شود.

## قواعد canonicalization

- ارقام فارسی `۰۱۲۳۴۵۶۷۸۹` و عربی `٠١٢٣٤٥٦٧٨٩` پیش از validation به ASCII تبدیل می‌شوند.
- مبلغ صحیح می‌تواند بدون جداکننده یا با گروه‌بندی سه‌رقمی معتبر توسط `,` یا `٬` وارد شود.
- مقدار اعشاری علاوه بر قواعد گروه‌بندی، ممیز `.` یا `٫` را می‌پذیرد و به نقطهٔ ASCII تبدیل می‌کند.
- گروه‌بندی ناقص، ترکیب دو نوع جداکننده، چند ممیز، حروف و چند علامت منفی رد می‌شوند.
- تاریخ و ساعت پیش از بررسی قالب به رقم ASCII تبدیل و با قالب canonical ذخیره می‌شوند.
- در تلفن و شناسه‌هایی مانند شماره چک، شماره پیگیری، شناسه سفارش و SKU فقط فاصله ابتدا/انتها حذف و رقم‌ها تبدیل می‌شوند؛ خط‌تیره، پرانتز، `+` و سایر punctuation حذف نمی‌شوند.

## محدوده schemaها

Normalization روی ورودی‌های اصلی کاتالوگ و قیمت، فروش و پرداخت، خرید و موجودی، دفتر اشخاص و چک، و کانال/سفارش آنلاین اعمال شده است. پاسخ‌ها همچنان `int`، `Decimal` یا `str` canonical قبلی را برمی‌گردانند.

## مسئولیت frontend

لایه frontend نیز در همین فاز تکمیل شد:

- formatterهای رقم، پول و مقدار در `frontend/src/numberUtils.ts` متمرکز شدند.
- `MoneyField` نمایش زندهٔ فارسی و سه‌رقمی را فراهم می‌کند، رقم فارسی/عربی/لاتین و جداکننده‌های رایج را می‌پذیرد و مقدار state/payload را به ریال عددی canonical تحویل می‌دهد.
- موقعیت cursor پس از تایپ، paste و backspace بر پایه تعداد رقم‌های سمت راست بازسازی می‌شود تا ویرایش وسط عدد مخرب نباشد.
- مبلغ‌های خرید، فروش، پرداخت، قیمت کالا، تخفیف، سند دستی، تسویه، چک و قیمت آنلاین از component مشترک استفاده می‌کنند.
- ورودی quantity و درصد اعشاری از پول جدا مانده و تبدیل ریال/تومان روی آن انجام نمی‌شود.
- فیلدهای پول در موبایل `inputMode=numeric` دارند.

## حفاظت از داده‌های قبلی

این فاز فقط ورودی‌های جدید را canonical می‌کند. داده‌های رشته‌ای قدیمی، به‌خصوص تلفن و شماره چک، بدون تغییر باقی می‌مانند. اگر پاک‌سازی آن‌ها لازم شود باید پس از بکاپ، گزارش dry-run و تأیید کاربر در یک migration جدا انجام شود.

## تست‌ها

- تست پارامتریک helper برای رقم فارسی، عربی، ورودی ترکیبی، مبلغ گروه‌بندی‌شده و اعشار
- رد صریح گروه‌بندی ناقص، جداکننده‌های مخلوط، چند ممیز و حروف
- حفظ punctuation تلفن و شناسه همراه با canonical شدن رقم‌ها
- canonical شدن تاریخ و ساعت فارسی
- تست endpoint دفتر حساب برای مبلغ، تلفن، تاریخ و ساعت محلی
- تست endpoint فروش برای مبلغ، مقدار اعشاری، تاریخ، ساعت و شماره پیگیری

پس از تکمیل frontend باید تایپ، paste، backspace، selection و حرکت cursor در عرض موبایل `390 × 844` و دسکتاپ آزمایش شود.

Build فرانت‌اند با `pnpm run build` موفق و ۹۷۴ ماژول بدون خطای TypeScript/Vite ساخته شد. frontend در حال حاضر test runner واحد ندارد؛ بنابراین آزمون تعاملی زیر پیش از تغییر وضعیت به done ضروری است:

1. مبلغ `1234567`، `۱۲۳۴۵۶۷` و `١٢٣٤٥٦٧` را در فرم فروش وارد کنید؛ هر سه باید `۱٬۲۳۴٬۵۶۷` نشان دهند.
2. عدد را paste کنید، چند رقم وسط آن را انتخاب و جایگزین کنید و backspace بزنید؛ cursor نباید به شکل مخرب جابه‌جا شود.
3. فروش آزمایشی را ثبت کنید و صحت مبلغ ذخیره‌شده را بررسی کنید؛ separator نباید وارد payload شده باشد.
4. همین آزمون را برای خرید، قیمت کالا، سند دستی، تسویه، چک و قیمت آنلاین تکرار کنید.
5. در مقدار کالا `۱٫۵` وارد کنید و بررسی کنید مانند مبلغ به تومان تبدیل نشده باشد.
6. موارد بالا را در viewport موبایل `۳۹۰ × ۸۴۴` تکرار و بازشدن keypad عددی و نبود اسکرول افقی را بررسی کنید.
