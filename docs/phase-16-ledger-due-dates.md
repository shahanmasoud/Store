# فاز ۱۶ — سررسید صریح و ممیزی‌شده اسناد دستی

## هدف و محدوده

این برش فقط سررسید اسناد دستی دفتر حساب را تکمیل می‌کند. برای حفاظت از اطلاعات مالی، تاریخ ثبت سند دیگر به‌صورت ضمنی سررسید محسوب نمی‌شود و هیچ تاریخ قدیمی به‌صورت حدسی پر نمی‌شود.

موارد تحویل‌شده:

- فیلد اختیاری `due_jalali_date` روی `ledger_entries`؛
- امکان ثبت سررسید هم‌زمان با ایجاد سند دستی؛
- امکان تعیین، تغییر یا پاک‌کردن سررسید فقط برای مدیر اصلی؛
- تاریخچه append-only شامل مقدار قبل و بعد، دلیل تغییر و snapshot هویت مدیر؛
- نمایش در API سررسیدها فقط وقتی موعد صریح ثبت شده و از تاریخ پیگیری عبور کرده باشد.

رابط مدیریت شامل ثبت سررسید اختیاری، برچسب وضعیت موعد، دیالوگ تعیین/تغییر/پاک‌کردن و تاریخچه حسابرسی است. تقویم یکپارچه، اعلان زمان‌بندی‌شده و ویرایش سایر مشخصات سند در این فاز نیست.

## قرارداد API

### ایجاد سند

`POST /api/v1/ledger/manual-entry` اکنون `due_jalali_date` اختیاری با قالب `1405/06/20` می‌پذیرد و آن را در پاسخ برمی‌گرداند. نبودن این فیلد یعنی سند فعلاً موعد مشخصی ندارد.

### تغییر سررسید

`PATCH /api/v1/ledger/entries/{entry_id}/due-date`

نمونه تعیین یا تغییر:

```json
{
  "due_jalali_date": "1405/06/20",
  "reason": "توافق با مشتری"
}
```

برای پاک‌کردن موعد، مقدار `due_jalali_date` باید صریحاً `null` ارسال شود. دلیل تغییر اجباری و غیرخالی است. عملیات فقط روی سندی مجاز است که دستی، فعال، باز و دارای مانده مثبت باشد؛ مقدار تکراری با پاسخ `409` رد می‌شود.

### تاریخچه ممیزی

`GET /api/v1/ledger/entries/{entry_id}/due-date/audits`

این مسیر فقط برای مدیر اصلی است و رخدادها را به ترتیب زمان و شناسه برمی‌گرداند. هر ردیف شامل تاریخ قبل/بعد، دلیل، زمان UTC و snapshot نام کاربری و نام مدیر است؛ بنابراین تغییر نام بعدی کاربر تاریخچه را مخدوش نمی‌کند.

### فهرست سررسیدها

`GET /api/v1/dues?jalali_date_to=1405/06/30`

فقط اسناد باز و فعال با `due_jalali_date` غیرخالی و کوچک‌تر یا مساوی تاریخ انتخابی برگردانده می‌شوند. `jalali_date` سند دیگر جایگزین سررسید نیست.

## مهاجرت و حفظ داده

migration شماره `0014_ledger_due_dates` ستون nullable و جدول `ledger_due_audits` را اضافه می‌کند. همه اسناد موجود با سررسید `null` باقی می‌مانند و هیچ backfill حدسی انجام نمی‌شود. پیش از اجرای migration روی محیط اصلی باید snapshot سازگار SQLite تهیه و integrity آن بررسی شود.

آزمون migration روی کپی دیتابیس محلی از revision `0013_product_image` انجام شد:

- revision نهایی: `0014_ledger_due_dates`؛
- `PRAGMA integrity_check`: `ok`؛
- تعداد سررسیدهای غیرخالیِ افزوده‌شده به سوابق قدیمی: صفر؛
- تعداد audit ساختگی برای سوابق قدیمی: صفر.

چرخه `downgrade` به `0013_product_image` و سپس `upgrade` دوباره به head نیز روی همان کپی اجرا شد؛ یک سند قدیمی حفظ شد، revision دوباره به `0014_ledger_due_dates` رسید و `integrity_check` همچنان `ok` بود.

## آزمون دستی کوتاه رابط کاربری

1. یک سند دستی باز بدون سررسید بسازید و مطمئن شوید در فهرست موعدها دیده نمی‌شود.
2. با حساب مدیر اصلی برای آن موعد و دلیل ثبت کنید؛ سپس موعد را تغییر دهید و تاریخچه سه مقدار «قبل/بعد/دلیل» را بررسی کنید.
3. موعد را پاک کنید و مطمئن شوید سند دوباره از یادآوری سررسید خارج می‌شود، اما خود سند و تاریخچه باقی می‌مانند.
4. همین عملیات را روی سند تسویه‌شده یا غیر دستی امتحان کنید؛ سیستم باید بدون تغییر داده آن را رد کند.
5. با کاربر زیرمدیریت مسیر تغییر و تاریخچه را امتحان کنید؛ تا زمان تعریف دسترسی ریزدانه باید پاسخ عدم مجوز نمایش داده شود.

## آزمون خودکار

آزمون‌های `backend/tests/test_ledger_cheques_dues.py` موارد ثبت اولیه، set/change/clear، canonical شدن رقم‌های فارسی، ترتیب و snapshot تاریخچه، no-op، تاریخ نامعتبر، سند مفقود، سند بسته/غیردستی/غیرفعال و پاسخ‌های `401/403` را پوشش می‌دهند.

نتیجه اجرای مجموعه کامل بک‌اند توسط عامل اصلی: `180 passed` با ۶ هشدار deprecation موجود در وابستگی‌ها/کدهای قبلی. تست اعداد frontend برابر ۳ از ۳ و build production با ۹۷۶ ماژول موفق بود.

ورود واقعی در Chrome و نمایش داشبورد روی کپی دیتابیس مهاجرت‌یافته موفق بود. به‌علت عمل‌نکردن کنترل خودکار ناوبری React در نشست Chrome، تست تعاملی نهایی دیالوگ و viewport موبایل همچنان در تست پذیرش کاربر قرار دارد و به‌عنوان QA کامل اعلام نمی‌شود.
