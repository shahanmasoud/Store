# بک‌لاگ تکمیل پنل مدیریت فروشگاه

این سند مرجع ثبت، پیاده‌سازی و ادامهٔ تست نیازهای پنل مدیریت است. هدف آن این است که هر قابلیت، وضعیت فعلی، شکاف باقی‌مانده، وابستگی‌ها و روش تست دستی مشخصی داشته باشد و داده‌های مالی موجود در زمان توسعه حفظ شوند.

## راهنمای وضعیت‌ها

- `planned`: برنامه‌ریزی شده و هنوز وارد پیاده‌سازی نشده است.
- `in progress`: پیاده‌سازی یا بررسی فعال است.
- `done`: پیاده‌سازی، تست خودکار و بازبینی دستی تکمیل شده است.
- `existing-but-incomplete`: بخشی از قابلیت وجود دارد، اما نیاز کاربر را کامل پوشش نمی‌دهد.

## ترتیب فعلی تست کاربر

کاربر تست پنل را به این ترتیب آغاز کرده است:

1. ورود به پنل مدیریت؛ تست اولیه انجام شده و ادامهٔ آن با تغییر رمز و مدیریت کاربران است.
2. تعریف کالاها؛ تست اولیه انجام شده و ادامهٔ آن شامل موجودی اولیه، قیمت خرید، اتصال فروشگاه و عکس کالا است.
3. تعریف مشتری‌ها و اشخاص؛ این بخش هنوز ناقص است و باید در اولویت اصلاح قرار بگیرد.

پس از این سه بخش، تست چک‌ها، اسناد نسیه، سررسیدها، گزارش‌ها و بکاپ دوره‌ای ادامه پیدا می‌کند.

## اصل حفاظت از اطلاعات

پیش از هر migration یا تغییر ساختار دیتابیس باید از دیتابیس واقعی PythonAnywhere و فایل‌های آپلودی بکاپ گرفته شود و بازیابی آن روی یک فایل موقت آزمایش شود. دیتابیس مالی، توکن‌ها و فایل‌های خصوصی نباید داخل GitHub commit شوند. migrationها باید تا حد ممکن افزایشی، nullable/defaultدار و بدون حذف سوابق باشند. در محیط production نباید دستور reset یا seed مخرب اجرا شود.

## بخش ۱ — ورود، امنیت و کاربران مدیریت

### ADM-001 — تغییر رمز عبور مدیر

- وضعیت: `in progress`
- نیاز: مدیر بتواند بعد از ورود، رمز عبور خودش را تغییر دهد.
- وضعیت فعلی: مدل `User` و ورود با نام کاربری/رمز وجود دارد؛ API فقط ورود و مشاهدهٔ کاربر جاری را پوشش می‌دهد.
- شکاف: endpoint تغییر رمز، بررسی رمز فعلی، سیاست رمز جدید، رابط کاربری و مدیریت نشست پس از تغییر رمز وجود ندارد.
- وابستگی‌ها: مدل و سرویس کاربران، امنیت JWT، فرم تنظیمات حساب.
- معیار پذیرش:
  - رمز فعلی پیش از تغییر بررسی شود.
  - رمز جدید و تکرار آن اعتبارسنجی شوند و رمز به‌صورت hash ذخیره شود.
  - پس از موفقیت، رمز قبلی برای ورود رد و رمز جدید پذیرفته شود.
  - خطاها و موفقیت با پیام فارسی روشن نمایش داده شوند.
  - توکن، hash یا رمز در log و پاسخ API افشا نشود.
- تست دستی دسکتاپ:
  1. با رمز فعلی وارد پنل شوید.
  2. رمز اشتباه را به‌عنوان رمز فعلی وارد کنید و ردشدن درخواست را ببینید.
  3. رمز معتبر جدید را ثبت کنید، خارج شوید و ورود با رمز قدیمی و جدید را امتحان کنید.
- تست دستی موبایل:
  1. همین مسیر را در عرض `390 × 844` اجرا کنید.
  2. باز و بسته‌شدن نمایش رمز، صفحه‌کلید، پیام validation و در دسترس بودن دکمهٔ ذخیره را بررسی کنید.
  3. نبود اسکرول افقی، بریدگی یا هم‌پوشانی dialog را تأیید کنید.

### ADM-002 — تعریف و مدیریت کاربر زیرمدیریت

- وضعیت: `implemented-awaiting-user-qa` — زیرساخت مجوز، API و رابط مدیریت کاربر، ممیزی و دسترسی محدود صندوقدار فروش کامل است؛ تست پذیرش دسکتاپ/موبایل باقی مانده است.
- نیاز: مدیر اصلی بتواند کاربر مدیریتی جدید با سطح دسترسی محدود تعریف کند.
- وضعیت فعلی: چهار مجوز بخشی با حالت پیش‌فرض بسته ثبت شده‌اند. مدیر اصلی می‌تواند زیرمدیر غیر‌اصلی بسازد، نام کامل و دسترسی فروش را تغییر دهد، حساب را غیرفعال و رمز موقت را بازنشانی کند. همه تغییرهای امنیتی audit می‌شوند و نشست قبلی باطل می‌شود. صندوقدار فقط API فروش و داده‌های محدود فرم فروش را می‌بیند و لغو فروش برای مدیر اصلی باقی مانده است.
- شکاف: سه مجوز آینده تا تکمیل audit عملیات مالی از payload مدیریت کاربر قابل فعال‌سازی نیستند؛ تست پذیرش مدیر و صندوقدار در دسکتاپ/موبایل باقی مانده است.
- وابستگی‌ها: ADM-001، طراحی RBAC، محافظت backend مستقل از مخفی‌کردن منوها در frontend.
- معیار پذیرش:
  - فقط مدیر مجاز بتواند کاربر ایجاد یا ویرایش کند.
  - نام کاربری یکتا، رمز امن، نام کامل، وضعیت فعال و نقش قابل تعیین باشند.
  - زیرمدیر فقط APIها و صفحات مجاز را باز کند و برای بقیه پاسخ `403` بگیرد.
  - غیرفعال‌سازی آخرین مدیر اصلی و غیرفعال‌سازی ناخواستهٔ کاربر جاری مسدود شود.
  - حذف به‌صورت غیرفعال‌سازی باشد و سابقهٔ فعالیت باقی بماند.
- تست دستی دسکتاپ: ایجاد زیرمدیر، ورود با آن، بررسی منوها و تلاش مستقیم برای دسترسی به API/صفحهٔ غیرمجاز.
- تست دستی موبایل: فهرست کاربران به‌شکل کارت بدون جدول عریض، دکمه‌های حداقل ۴۴ پیکسل و فرم بدون overflow بررسی شود.

  - مقدار، قیمت خرید و دلیل اصلاح اعتبارسنجی شوند.
  - میانگین بهای موزون و گزارش ارزش انبار درست به‌روز شوند.
  - ذخیرهٔ موجودی و تراکنش به‌صورت اتمیک باشد.

- تست دستی دسکتاپ: ثبت کالای جدید با موجودی اولیه، افزایش و کاهش اصلاحی، بررسی موجودی، میانگین بها و گردش انبار.

- نیاز: کالاهای سمت فروشگاه از داده‌های واقعی مدیریت و دیتابیس خوانده شوند.
- وضعیت فعلی: فروشگاه از API عمومی فقط‌خواندنی و بدون token کانال، اطلاعات فعال دیتابیس و موجودی پس از رزرو را می‌گیرد؛ loading، empty، error/retry، جست‌وجو، دسته و سبد واقعی پیاده شده‌اند.
- شکاف: استقرار روی PythonAnywhere و تأیید پذیرش کاربر باقی مانده است.
- وابستگی‌ها: PRD-001، API کاتالوگ عمومی، سیاست نمایش کالای ناموجود، دسته و واحد، امنیت توکن کانال.
- معیار پذیرش:

  - تغییر و غیرفعال‌سازی کالا در مدیریت پس از refresh در فروشگاه منعکس شود.
  - کالای غیرفعال نمایش داده نشود و رفتار کالای ناموجود مشخص باشد.
  - سبد خرید بر اساس `variant_id` واقعی کار کند.
  - loading، empty، error و retry فارسی وجود داشته باشند.
- تست دستی دسکتاپ: تغییر نام/قیمت یک کالا در مدیریت، refresh فروشگاه، جست‌وجو، فیلتر و افزودن آن به سبد.
