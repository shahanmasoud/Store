# فاز ۳۱ — ممیزی خواندنی اتصال فروش‌های قدیمی به دفتر

## محدوده تحویل

این فاز فقط گزارش `dry-run` می‌سازد. ابزار هیچ گزینهٔ apply، backfill، migration یا نوشتن ندارد و SQLite را با `mode=ro` و `PRAGMA query_only` باز می‌کند.

```bash
cd backend
python -m app.scripts.reconcile_sale_ledger
```

برای دیتابیس آزمایشی می‌توان `--database-url sqlite:///...` داد. مسیر دیتابیس، نام و تلفن مشتری یا متن اسناد در خروجی چاپ نمی‌شود.

## گروه‌های خروجی

- `missing`: فروش فعال، متصل به مشتری و مانده‌دار است، اما سندی با پیوند صریح `source_type=sale` و `source_id=invoice_id` ندارد.
- `exact`: دقیقاً یک سند پیوندخورده وجود دارد و شخص، نوع بدهکار، مبلغ، تاریخ، ساعت، سررسید، وضعیت و تخصیص‌های تسویه با فاکتور سازگارند.
- `conflict`: پیوند تکراری یا ناسازگار، سند متصل به فاکتور نامعتبر، لغو ناسازگار، یا source بدون فاکتور وجود دارد. زوج معتبر فاکتور/سند لغوشده conflict محسوب نمی‌شود.

شباهت مبلغ، تاریخ یا سند دستی هرگز برای matching کافی نیست؛ بنابراین ابزار احتمال اتصال اشتباه رکوردهای مالی را به نفع گزارش `missing` رد می‌کند. ترتیب آرایه‌ها بر اساس شناسه و JSON با کلیدهای مرتب، deterministic است.

## exit code

- `0`: فقط رکوردهای exact وجود دارند و اقدامی لازم نیست.
- `2`: حداقل یک missing یا conflict برای بازبینی وجود دارد.
- `1`: خطای عملیاتی؛ خروجی فقط نام کلاس خطا را بدون مسیر یا متن حساس برمی‌گرداند.

## شواهد خودکار

- تست هدفمند command: ۷ تست موفق؛ مجموعه command، migration و فروش: ۲۶ تست موفق.
- کل backend پس از این فاز: ۲۴۲ تست موفق.
- سناریوی فروش لغوشدهٔ معتبر و مسیر دیتابیس دارای فاصله/`#` نیز پوشش داده شده‌اند.
- تست hash فایل و snapshot منطقی ثابت می‌کند دو اجرای گزارش هیچ تغییری در دیتابیس ایجاد نمی‌کنند.
- تست matching ثابت می‌کند یک سند دستی با همان مشتری/مبلغ به فروش نسبت داده نمی‌شود.
- تست conflict ناسازگاری شخص، تخصیص و source یتیم را پوشش می‌دهد.

## گام بعدی و محدودیت انتشار

گزارش روی production اجرا نشده و هیچ رکورد قدیمی تغییر نکرده است. طراحی apply فقط پس از تهیه و verify بکاپ، بازبینی JSON واقعی، تعریف سیاست حل هر conflict و تأیید صریح کاربر مجاز است. این فاز deploy، merge یا push نشده است.
