# فاز ۲۰ — دسترسی محدود کالا، خرید و انبار

## هدف و مرز امنیتی

این مرحله مجوز ذخیره‌شده `can_catalog_inventory` را به یک دسترسی عملیاتی واقعی تبدیل می‌کند. مدیر اصلی می‌تواند آن را هنگام ساخت یا ویرایش زیرمدیر فعال کند. `is_superuser`، `can_ledger` و `can_cheques_reports` همچنان خارج از allow-list هستند و ارسالشان با `422` رد می‌شود.

تغییر `can_catalog_inventory` مانند تغییر دسترسی فروش، `token_version` را افزایش می‌دهد؛ بنابراین token قبلی بلافاصله با `401` باطل می‌شود. تصویر قبل و بعد شامل این مجوز در `user_admin_audits` ذخیره می‌شود و رمز/hash وارد audit نمی‌شود.

Superuser همیشه از بررسی permission عبور می‌کند. فرانت فقط برای تجربه کاربری منو و اکشن را پنهان می‌کند؛ تصمیم نهایی در dependencyهای FastAPI گرفته می‌شود.

## API مدیریت کاربر

`POST /api/v1/users` و `PATCH /api/v1/users/{id}` اکنون `can_catalog_inventory` را در کنار `can_sales` می‌پذیرند. دو مجوز را می‌توان مستقل یا هم‌زمان فعال کرد. نام کاربری immutable و حساب ساخته‌شده همیشه non-super باقی می‌ماند.

## سیاست endpointها

- router کاتالوگ و router خرید/انبار به `require_permission("can_catalog_inventory")` متصل‌اند.
- create/updateهای روزمره برای دارنده مجوز باز هستند.
- endpointهای مخرب dependency اضافه `require_superuser` دارند؛ واردکردن مستقیم URL نیز `403` می‌دهد.
- `POST /inventory/adjustments` actor را از کاربر permissioned جاری می‌گیرد؛ شناسه، username و نام کامل او در همان audit موجودی ثبت می‌شود.
- storefront عمومی، ورود بله و APIهای عمومی کانال آنلاین تغییری نکرده‌اند.
- گزارش‌ها در این مرحله فقط برای مدیر اصلی باقی مانده‌اند.

## آزمون خودکار

ماتریس خودکار موارد زیر را پوشش می‌دهد:

- پذیرش `can_catalog_inventory` در create/update و رد دو مجوز آینده و `is_superuser`؛
- create/update واقعی واحد، دسته، کالا و گونه توسط مسئول انبار؛
- مشاهده خرید، موجودی و گردش انبار؛
- ثبت موجودی اولیه و تطبیق actor audit با همان زیرمدیر؛
- `403` برای حذف رکورد، حذف عکس، غیرفعال‌سازی قاعده و لغو خرید؛
- `403` مستقیم برای فروش، دفتر، گزارش و آنلاین در نقش فقط انبار؛
- حفظ محدودیت صندوقدار فقط‌فروش؛
- نقش ترکیبی فروش+انبار؛
- ابطال token پس از برداشتن مجوز انبار و snapshot قبل/بعد audit.

فرمان هدف:

```powershell
python -m pytest tests/test_user_admin_permissions.py tests/test_catalog.py tests/test_purchases_inventory.py -q
```

نتیجه هدف‌گیری‌شده این مرحله: `71 passed`. سپس عامل اصلی مجموعه کامل backend را اجرا کرد: `201 passed` و شش warning قدیمی deprecation، بدون خطای آزمون. تست اعداد frontend برابر ۳ از ۳ و build production با ۹۷۶ ماژول موفق بود.

رابط مدیریت کاربران، منو، خانه نقش‌محور و اکشن‌های محافظت‌شده به این مجوز متصل‌اند. کاربر غیرمدیر عملیات مخرب و مدیریت تصویر را نمی‌بیند؛ صفحه خانه او فقط در صورت داشتن این مجوز گزارش موجودی را درخواست می‌کند و هیچ گزارش مالی یا سررسیدی بدون مجوز فراخوانی نمی‌شود.

## تست دستی پس از اتصال فرانت

### دسکتاپ

1. مدیر اصلی یک کاربر فقط با دسترسی «کالا، خرید و انبار» بسازد.
2. با آن کاربر وارد شوید؛ فقط صفحه‌های کالا، خرید و انبار باید دیده شوند.
3. واحد، دسته، کالا و گونه بسازید؛ یک خرید و یک اصلاح موجودی ثبت کنید.
4. دکمه‌های غیرفعال‌سازی، عکس و لغو خرید نباید در دسترس باشند و URL مستقیم باید `403` بدهد.
5. مدیر دسترسی انبار را بردارد؛ نشست باز باید پایان یابد و ورود بعدی صفحه‌های انبار را نشان ندهد.

### موبایل `390 × 844`

1. Drawer فقط بخش‌های مجاز را نشان دهد و هیچ اسکرول افقی نداشته باشد.
2. فرم‌های کالا، خرید و اصلاح موجودی با صفحه‌کلید عددی و دکمه‌های حداقل ۴۴ پیکسل آزمایش شوند.
3. تاریخچه اصلاح موجودی باید نام همان زیرمدیر را بدون بریدگی نمایش دهد.
4. نقش ترکیبی فروش+انبار را نیز بررسی کنید؛ جابه‌جایی بین بخش‌ها نباید کارت یا فرم را هم‌پوشان کند.
