# فاز ۲۶ — سررسید پرداخت نسیه فروش (backend)

## محدوده تحویل

- افزودن، تغییر و حذف سررسید پرداخت `pending` متعلق به فاکتور فعال
- ثبت تاریخچه append-only شامل مقدار قبل و بعد، دلیل و هویت کاربر
- دسترسی فقط برای مدیر اصلی یا کاربر دارای `can_sales`
- optimistic concurrency اتمیک؛ در تغییر هم‌زمان فقط یک درخواست موفق می‌شود
- عدم ایجاد یا تغییر رکورد دفتر اشخاص در این برش، برای جلوگیری از دوباره‌شماری بدهی

## قرارداد API

- `PATCH /api/v1/sales/payments/{payment_id}/due-date`
- `GET /api/v1/sales/payments/{payment_id}/due-date/audits`

برای حذف سررسید، مقدار `due_jalali_date` برابر `null` ارسال می‌شود. درخواست ویرایش باید `reason` و `expected_updated_at` نسخه مشاهده‌شده را نیز داشته باشد.

## کنترل‌های ایمنی

- پرداخت دریافت‌شده و فاکتور باطل/غیرفعال قابل تغییر نیست.
- تاریخ جلالی نامعتبر، تغییر بدون اثر و نسخه stale رد می‌شوند.
- UPDATE و ثبت audit در یک transaction هستند.
- migration `0018_payment_due_audits` فقط جدول audit را اضافه و نسخه رکوردهای قدیمی را از `created_at_utc` مقداردهی می‌کند؛ رکورد مالی حذف نمی‌شود.

## تست خودکار

- `tests/test_sales.py`: هفده تست موفق
- کل backend: دویست‌وبیست تست موفق
- تست race با دو session: دقیقاً یک پاسخ موفق و یک تعارض ۴۰۹
- migration از دیتابیس خالی تا head روی فایل موقت اجرا شد.

## تست دستی پس از تکمیل UI

یک فاکتور فعال با پرداخت pending باز کنید؛ سررسید را اضافه، تغییر و حذف کنید و پس از refresh تاریخچه را ببینید. سپس همین سناریو را در عرض `390 × 844` با صفحه‌کلید باز و بدون overflow تکرار کنید. پرداخت received و فاکتور باطل نباید دکمه ویرایش داشته باشند.
