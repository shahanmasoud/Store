# فاز ۱۹ — زیرمدیر امن و دسترسی صندوقدار فروش

## محدوده تحویل

این برش نخستین مرحله ADM-002 است و مرز دسترسی واقعی backend را همراه رابط مدیریت کاربران تحویل می‌دهد. حساب زیرمدیر نمی‌تواند مدیر اصلی شود و در این مرحله فقط مجوز «فروش روزانه» قابل واگذاری است.

## مدل و migration

migration `0016_user_permissions` چهار ستون Boolean زیر را با مقدار پیش‌فرض `false` به `users` اضافه می‌کند:

- `can_sales`
- `can_catalog_inventory`
- `can_ledger`
- `can_cheques_reports`

کاربران قدیمی بدون تغییر یا حذف داده، هر چهار مقدار را `false` می‌گیرند. مدیر اصلی مستقل از مقدار ستون‌ها، در پاسخ API هر چهار مجوز مؤثر را `true` دریافت می‌کند.

جدول `user_admin_audits` یک تاریخچه افزایشی با actor، target، action، تصویر امن قبل/بعد، دلیل و زمان UTC نگه می‌دارد. hash رمز، رمز موقت و `token_version` هرگز در snapshot نوشته نمی‌شوند.

## قرارداد مدیریت کاربران

همه مسیرهای زیر Bearer token مدیر اصلی می‌خواهند:

- `GET /api/v1/users`: همه کاربران فعال و غیرفعال.
- `POST /api/v1/users`: `username`، `full_name`، `temporary_password`، `can_sales` و `reason`؛ خروجی همیشه non-super است.
- `PATCH /api/v1/users/{id}`: فقط `full_name`، `can_sales` و `reason`. نام کاربری immutable است.
- `POST /api/v1/users/{id}/deactivate`: دلیل اجباری و غیرفعال‌سازی نرم.
- `POST /api/v1/users/{id}/reset-password`: رمز موقت جدید و دلیل اجباری.

Schemaها `extra=forbid` دارند. ارسال `is_superuser` یا سه مجوز آینده با `422` رد می‌شود. تغییر مجوز، غیرفعال‌سازی و reset رمز `token_version` را افزایش می‌دهند؛ بنابراین token قبلی بلافاصله `401` می‌گیرد. غیرفعال‌سازی یا reset خود از API مدیریت کاربران ممنوع است و حساب مدیر اصلی از این مسیر تغییر نمی‌کند.

## ماتریس دسترسی این برش

| مسیر | مدیر اصلی | صندوقدار `can_sales` | زیرمدیر بدون مجوز |
| --- | --- | --- | --- |
| login، me، تغییر رمز خود | مجاز | مجاز | مجاز |
| فهرست/ثبت/مشاهده فروش و دفتر روزانه | مجاز | مجاز | `403` |
| `GET /sales/form-options` | مجاز | مجاز | `403` |
| لغو فروش | مجاز | `403` | `403` |
| کالا، خرید، انبار، دفتر، چک، گزارش و مدیریت آنلاین | مجاز | `403` | `403` |
| storefront عمومی و ورود مشتری بله | عمومی و بدون تغییر | عمومی و بدون تغییر | عمومی و بدون تغییر |
| مدیریت کاربران | مجاز | `403` | `403` |

`GET /api/v1/sales/form-options` فقط داده لازم برای فرم صندوق را برمی‌گرداند: گونه‌های فعال، موجودی و مشتریان فعال از نوع customer/both. این مسیر مانع نیاز صندوقدار به APIهای گسترده کالا، انبار یا دفتر حساب می‌شود.

## آزمون خودکار

فایل `tests/test_user_admin_permissions.py` موارد زیر را پوشش می‌دهد:

- الزام login و superuser برای `/users`؛
- رد فیلدهای escalation؛
- مجوز مؤثر مدیر اصلی و پیش‌فرض بسته زیرمدیر؛
- دسترسی صندوقدار فقط به فروش و رد مستقیم سایر APIها؛
- ممنوعیت لغو فروش؛
- ابطال token پس از تغییر مجوز، reset رمز و غیرفعال‌سازی؛
- محافظت از عملیات روی حساب خود و هر حساب مدیر اصلی؛
- snapshotهای audit بدون رمز/hash؛
- ارتقای دیتابیس legacy و `PRAGMA integrity_check`.

در بازبینی یکپارچه عامل اصلی پس از اتصال فرم فروش به مسیر حداقلی `form-options`، مجموعه کامل آزمون‌ها با نتیجه `200 passed` اجرا شد. شش warning موجود همگی deprecationهای قبلی کتابخانه‌ها هستند و خطای آزمون نیستند. تست اعداد frontend برابر ۳ از ۳ و build production با ۹۷۶ ماژول موفق بود.

رابط مدیر شامل فهرست کارت‌محور، ساخت صندوقدار، ویرایش نام/مجوز، reset رمز موقت و غیرفعال‌سازی با دلیل است. منو و خانه صندوقدار فقط فروش را نشان می‌دهند و فرم فروش برای دریافت کالا، موجودی و مشتری فقط از `/sales/form-options` استفاده می‌کند؛ بنابراین صندوقدار به API گسترده کاتالوگ، انبار یا دفتر دسترسی ندارد.

آزمون migration روی کپی دیتابیس موجود تا revision `0016_user_permissions` با `PRAGMA integrity_check = ok` انجام شد؛ کاربر مدیر قبلی حفظ شد و همه permissionهای ذخیره‌شده قدیمی صفر ماندند، درحالی‌که مدیر اصلی در پاسخ API مجوز مؤثر کامل می‌گیرد.

## تست دستی پس از ساخت رابط کاربری

### دسکتاپ

1. با مدیر اصلی یک صندوقدار با رمز موقت و دسترسی فروش بسازید.
2. با حساب صندوقدار وارد شوید؛ فقط خانه محدود و فروش باید قابل مشاهده باشد.
3. کالا و مشتری را از داده محدود فرم انتخاب و یک فروش آزمایشی ثبت کنید.
4. URL یا API کالا، انبار، دفتر و گزارش را مستقیم امتحان کنید و `403` بگیرید.
5. تلاش برای لغو فروش باید رد شود.
6. مدیر اصلی دسترسی فروش را خاموش کند؛ نشست باز صندوقدار باید به ورود مجدد هدایت شود و نشست تازه نیز فروش را باز نکند.

### موبایل `390 × 844`

1. کارت‌های کاربران، فرم تمام‌صفحه و کنترل دسترسی حداقل ۴۴ پیکسل بررسی شوند.
2. با صندوقدار وارد شوید و نبود آیتم‌های غیرمجاز در Drawer را تأیید کنید.
3. فرم فروش، انتخاب کالا/مشتری و ثبت نهایی بدون overlap یا اسکرول افقی آزمایش شود.
4. پس از قطع دسترسی توسط مدیر، پیام پایان نشست باید روشن باشد و draft ثبت‌نشده تا حد امکان حفظ شود.
