# فاز ۱۰: ورود مشتری با بازوی بله

## هدف و محدوده

این فاز فقط ورود مشتری به فروشگاه را فراهم می‌کند. ورود مدیر، پنل مدیریت و سطح دسترسی مدیر بدون تغییر باقی می‌مانند. صفحه پروفایل مشتری، ویرایش مشخصات، تاریخچه سفارش و اتصال شماره موبایل به فازهای بعد منتقل شده‌اند.

خروجی قابل تحویل این فاز:

- ساخت درخواست ورود یک‌بارمصرف با اعتبار دقیقاً ۲ دقیقه؛
- هدایت کاربر موبایل به بازوی بله؛
- نمایش QR قابل اسکن در دسکتاپ؛
- دریافت تأیید کاربر از Webhook بازو؛
- ورود خودکار مرورگر اولیه پس از تأیید؛
- نگهداری حداقلی هویت بله و صدور نشست مشتری؛
- پوشش حالت‌های loading، pending، approved، expired، canceled و error؛
- رابط فارسی RTL و واکنش‌گرا با هدف لمس حداقل ۴۴ پیکسل.

## جریان تجربه کاربری

### موبایل

1. مشتری روی «ورود با بله» می‌زند.
2. سرور یک challenge با شناسه تصادفی، کد شش‌رقمی و زمان انقضای ۱۲۰ ثانیه می‌سازد.
3. دکمه، لینک `https://ble.ir/<BOT_USERNAME>?start=<CODE>` را باز می‌کند.
4. بازو پیام `/start <CODE>` را دریافت می‌کند و دکمه «تأیید ورود» را نشان می‌دهد.
5. مشتری تأیید می‌کند؛ Webhook challenge را به شناسه کاربر بله متصل و approved می‌کند.
6. بازو یک دکمه امن «بازگشت به فروشگاه» با URL شامل شناسه عمومی challenge می‌فرستد.
7. سایت challenge را فقط یک‌بار exchange می‌کند، JWT مشتری را می‌گیرد و کاربر را به فروشگاه برمی‌گرداند.

### دسکتاپ

1. مشتری روی «ورود با بله» می‌زند.
2. Dialog ورود، QR همان deep-link، کد خوانا و شمارش معکوس دو دقیقه‌ای را نمایش می‌دهد.
3. مشتری QR را با موبایل اسکن و در بازو ورود را تأیید می‌کند.
4. مرورگر دسکتاپ هر دو ثانیه وضعیت challenge را بررسی می‌کند.
5. پس از approved شدن، exchange یک‌بارمصرف انجام و نشست مشتری ذخیره می‌شود؛ Dialog با پیام موفقیت بسته می‌شود.

اگر deep-link در یک نسخه بله payload را منتقل نکند، کد شش‌رقمی در UI باقی می‌ماند و مشتری می‌تواند آن را دستی برای بازو ارسال کند.

## قرارداد API

Base path: `/api/v1/auth/bale`

### `POST /challenges`

ورودی:

```json
{"return_path": "/"}
```

خروجی:

```json
{
  "id": "opaque-random-id",
  "code": "123456",
  "status": "pending",
  "expires_at_utc": "2026-09-04T12:02:00Z",
  "expires_in_seconds": 120,
  "bot_url": "https://ble.ir/example_bot?start=123456",
  "poll_after_seconds": 2
}
```

### `GET /challenges/{id}`

وضعیت جاری را با یکی از مقادیر `pending`، `approved`، `consumed` یا `expired` برمی‌گرداند. این endpoint هیچ JWT یا اطلاعات هویتی بله را افشا نمی‌کند.

### `POST /challenges/{id}/exchange`

فقط challenge تأییدشده و مصرف‌نشده را به نشست مشتری تبدیل می‌کند. پاسخ شامل `access_token` و اطلاعات حداقلی کاربر است. درخواست دوم با همان challenge رد می‌شود.

### `GET /me`

نشست مشتری را با Bearer token اعتبارسنجی می‌کند و فقط شناسه داخلی، نام نمایشی و provider را برمی‌گرداند. این endpoint صفحه پروفایل ایجاد نمی‌کند.

### `POST /webhook/{webhook_secret}`

Updateهای بله را دریافت می‌کند:

- پیام `/start <CODE>` یا خود کد: ارسال درخواست تأیید؛
- callback با `bale_login_confirm:<CODE>`: تأیید challenge و پاسخ به callback؛
- سایر پیام‌ها: راهنمای کوتاه فارسی.

مسیر webhook با یک secret مستقل از توکن بازو محافظت می‌شود. توکن بازو هرگز به فرانت‌اند، پاسخ API، لاگ برنامه یا GitHub وارد نمی‌شود.

## مدل داده

### `customer_accounts`

- `id`
- `provider` با مقدار `bale`
- `provider_user_id`، یکتا در هر provider
- `display_name` و `provider_username` به‌صورت اختیاری
- `is_active`
- `created_at_utc` و `last_login_at_utc`

### `bale_login_challenges`

- `id` به شکل UUID تصادفی و عمومی
- `code_hash`؛ کد خام در دیتابیس ذخیره نمی‌شود
- `status`
- `return_path` فقط مسیر داخلی مجاز
- `bale_user_id` پس از تأیید
- `expires_at_utc`، `approved_at_utc` و `consumed_at_utc`
- `created_at_utc`

## قواعد امنیتی

- TTL دقیق challenge برابر ۱۲۰ ثانیه است.
- کد با مولد امن ساخته و فقط hash آن ذخیره می‌شود.
- شناسه challenge تصادفی و غیرقابل حدس است.
- تأیید فقط از Webhook محافظت‌شده پذیرفته می‌شود.
- تأیید هویت نیز اتمیک است؛ اولین callback معتبر هویت challenge را قفل می‌کند و callback کاربر دیگری نمی‌تواند آن را بازنویسی کند.
- exchange اتمیک و فقط یک‌بار ممکن است.
- challenge منقضی یا مصرف‌شده JWT دریافت نمی‌کند.
- `return_path` فقط با `/` شروع می‌شود و URL خارجی پذیرفته نمی‌شود.
- داده ذخیره‌شده از بله حداقلی است؛ شماره موبایل در این فاز درخواست یا ذخیره نمی‌شود.
- JWT مشتری دارای claim نوع `customer` است و با توکن مدیر اشتباه گرفته نمی‌شود. در این فاز مطابق الگوی فعلی پروژه با کلید جداگانه `store_customer_token` در مرورگر نگهداری می‌شود؛ انتقال آن به cookie امن HttpOnly یک hardening مستقل در فاز بعدی است.
- UI هرگز توکن بازو یا webhook secret را دریافت نمی‌کند.

## تنظیمات محیطی

```dotenv
BALE_BOT_TOKEN=
BALE_BOT_USERNAME=
BALE_WEBHOOK_SECRET=
BALE_LOGIN_TTL_SECONDS=120
BALE_POLLING_FALLBACK=false
PUBLIC_BASE_URL=https://example.pythonanywhere.com
```

در نبود تنظیمات واقعی بازو، ساخت challenge با خطای سرویس پیکربندی‌نشده پاسخ می‌دهد؛ تست‌ها از gateway جعلی استفاده می‌کنند و به شبکه بله وابسته نیستند.

روی PythonAnywhere باید دسترسی خروجی سرور به `tapi.bale.ai` نیز با اجرای اسکریپت تنظیم Webhook بررسی شود. اگر سرویس میزبانی اتصال را محدود کرد، فعال‌شدن ورود واقعی منوط به مجازشدن این دامنه یا استفاده از پلن دارای دسترسی خروجی است.

اگر شبکه بله نتواند دامنه PythonAnywhere را مستقیماً فراخوانی کند، مقدار `BALE_POLLING_FALLBACK=true` فعال می‌شود. در این حالت webhook بله حذف و یک worker سبک داخل وب‌اپ updateها را با long polling دریافت می‌کند؛ همان endpoint و قواعد امنیتی پردازش حفظ می‌شوند. این حالت برای میزبانی فعلی پروژه در نظر گرفته شده و نباید هم‌زمان با webhook فعال باشد.

## راه‌اندازی Webhook

پس از ساخت بازو، مقادیر محیطی روی سرور تنظیم می‌شوند و سپس، بدون چاپ‌شدن توکن یا secret، فرمان زیر اجرا می‌شود:

```bash
cd ~/Store/backend
set -a
source ~/.store.env
set +a
~/.virtualenvs/store/bin/python -m app.scripts.configure_bale_webhook
```

اسکریپت ابتدا `getMe` را بررسی می‌کند تا نام بازو با توکن منطبق باشد و سپس Webhook HTTPS را روی endpoint همین سایت تنظیم می‌کند. پس از تغییر URL یا secret باید این فرمان دوباره اجرا شود.

## حالات رابط

- `idle`: معرفی کوتاه و دکمه شروع؛
- `creating`: دکمه غیرفعال با progress؛
- `pending`: QR/دکمه بله، کد، شمارش معکوس و راهنمای سه‌مرحله‌ای؛
- `approved`: بازخورد موفق و exchange خودکار؛
- `expired`: توضیح روشن و دکمه «دریافت کد جدید»؛
- `error`: پیام قابل اقدام و تلاش دوباره؛
- `authenticated`: دکمه آرام «وارد شده‌اید» بدون ایجاد صفحه پروفایل.

در حالت واردشده، کاربر می‌تواند از همان Dialog از حساب مشتری خارج شود. این عمل فقط نشست محلی مشتری را پاک می‌کند و هیچ تغییری در حساب بله یا ورود مدیر نمی‌دهد.

## تست خودکار مورد انتظار

- ساخت challenge با TTL برابر ۱۲۰ ثانیه؛
- یکتایی و hash شدن کد؛
- رد `return_path` خارجی؛
- pending قبل از Webhook؛
- رد Webhook با secret اشتباه؛
- تأیید از callback کاربر بله؛
- جلوگیری از بازنویسی هویت challenge تأییدشده؛
- ساخت یا بازیابی مشتری بر پایه `bale_user_id`؛
- exchange موفق و یک‌بارمصرف؛
- رد challenge منقضی و مصرف‌شده؛
- عدم افشای توکن یا شناسه بله در status عمومی؛
- تست UI برای شروع، pending، expiry، error و موفقیت؛
- QA دستی در عرض‌های ۳۹۰ و ۱۴۴۰ پیکسل بدون overflow.

## تست دستی کوتاه

1. در دسکتاپ «ورود با بله» را بزنید و QR، کد و شمارش معکوس `۲:۰۰` را ببینید.
2. QR را اسکن و در بازو «تأیید ورود» را بزنید؛ Dialog دسکتاپ باید خودکار موفق شود.
3. در موبایل دکمه ورود را بزنید؛ بازو باید باز شود و پس از تأیید، دکمه بازگشت به فروشگاه نمایش داده شود.
4. یک challenge را بیش از دو دقیقه رها کنید؛ باید منقضی شود و امکان دریافت کد تازه وجود داشته باشد.
5. refresh فروشگاه باید نشست مشتری را حفظ کند؛ هیچ صفحه پروفایلی نباید نمایش داده شود.
6. روی نام مشتری بزنید و «خروج از حساب» را انتخاب کنید؛ دکمه باید دوباره به «ورود با بله» تبدیل شود و نشست مدیر تغییر نکند.

## نتیجه پیاده‌سازی و QA این فاز

- ۱۳ تست اختصاصی ورود بله پاس شد؛
- کل مجموعه بک‌اند با ۱۱۱ تست پاس شد؛
- build تولید React و build قابل استقرار PythonAnywhere موفق بود؛
- مهاجرت SQLite از نسخه خالی تا revision `0008_bale_customer_login` اجرا شد؛
- Chrome دسکتاپ در عرض ۱۴۴۰ پیکسل: QR، کد شش‌رقمی، شمارش معکوس و polling بدون overflow تأیید شد؛
- Chrome موبایل در عرض ۳۹۰ پیکسل: QR حذف، دکمه مستقیم بازو نمایش داده شد و کنترل‌های اصلی حداقل ۴۴ پیکسل بودند؛
- سناریوی end-to-end محلی از ساخت challenge تا callback بازو، exchange و نمایش کاربر واردشده موفق بود؛
- خروج محلی مشتری، بازگشت دکمه ورود و حفظ جدایی از نشست مدیر در Chrome تأیید شد؛
- در QA، تفسیر محلی زمان بدون offset کشف و اصلاح شد؛ API اکنون `expires_at_utc` را صریحاً با offset UTC برمی‌گرداند و تست رگرسیون دارد.

تست واقعی روی شبکه بله هنوز به `BALE_BOT_TOKEN`، نام بازوی واقعی و دامنه عمومی HTTPS نیاز دارد و پس از تنظیم خصوصی این مقادیر روی میزبان انجام می‌شود.

## منابع سازگاری API بله

- نمونه‌های رسمی بله، آدرس Bot API یعنی `https://tapi.bale.ai/`، ساخت توکن توسط `@Bot_Father` و امکان webhook را نشان می‌دهند: <https://github.com/balemessenger/bale-bot-samples>
- نمونه رسمی webhook در API جدید: <https://github.com/balemessenger/bale-bot-samples/blob/master/new_api_example/conversationbot.py>

از آنجا که مستند عمومی بله درباره deep-link payload کامل نیست، لینک `?start=<CODE>` در استقرار واقعی با بازوی نهایی smoke-test می‌شود؛ ارسال دستی همان کد شش‌رقمی همیشه به‌عنوان مسیر جایگزین در UI و webhook پشتیبانی می‌شود.
