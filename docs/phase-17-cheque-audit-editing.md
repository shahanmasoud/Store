# فاز ۱۷ — ویرایش امن و ممیزی چک‌ها

## هدف و محدوده

این مرحله backend چک‌های دریافتی و پرداختی را برای ویرایش کنترل‌شده و حفظ سوابق مالی تکمیل می‌کند. هیچ مسیر حذف سختی اضافه نشده است؛ ابطال همچنان یک رویداد ثبت‌شده است و خود چک در دیتابیس و فهرست تاریخی باقی می‌ماند.

موارد تحویل‌شده:

- ایجاد چک و تمام رویدادهای چرخه عمر فقط توسط مدیر اصلی تا زمان طراحی RBAC ریزدانه؛
- ویرایش مشخصات فقط برای چک فعال با وضعیت `pending`؛
- optimistic concurrency با `expected_updated_at` برای جلوگیری از ذخیره فرم قدیمی؛
- تاریخچه append-only برای create، update و event با مقدار کامل قبل و بعد و snapshot هویت مدیر؛
- legacy snapshot برای چک‌های موجود، بدون تغییر مبلغ، وضعیت یا سایر مشخصات؛
- ترتیب قطعی رویدادها بر اساس تاریخ، ساعت و شناسه؛
- حفظ چک ابطال‌شده و رویدادها بدون `DELETE`.

## قرارداد API

### ایجاد

`POST /api/v1/cheques` اکنون فقط برای مدیر اصلی مجاز است. پاسخ علاوه بر مشخصات قبلی، `created_at_utc` و `updated_at_utc` را برمی‌گرداند. ایجاد چک و audit مربوط به آن در یک transaction ثبت می‌شوند.

### ویرایش

`PATCH /api/v1/cheques/{cheque_id}`

فیلدهای قابل ویرایش عبارت‌اند از:

- `person_id` (می‌تواند `null` شود)؛
- `bank_name`؛
- `cheque_number`؛
- `amount_rial`؛
- `issue_jalali_date`؛
- `due_jalali_date`؛
- `note` (می‌تواند `null` شود).

دو فیلد کنترلی نیز اجباری‌اند:

```json
{
  "reason": "اصلاح اطلاعات روی برگه چک",
  "expected_updated_at": "2026-09-08T10:15:30.123456Z"
}
```

`expected_updated_at` باید دقیقاً از آخرین پاسخ API گرفته شود. اگر چک پس از بازشدن فرم تغییر کرده باشد پاسخ `409` برمی‌گردد و کاربر باید اطلاعات تازه را دریافت کند. no-op، وضعیت غیرقابل ویرایش و چک غیرفعال نیز بدون تغییر داده با `409` رد می‌شوند. شخص مرتبط باید موجود و فعال باشد و ترتیب تاریخ صدور/سررسید دوباره اعتبارسنجی می‌شود.

### رویدادها و ابطال

`POST /api/v1/cheques/{cheque_id}/events` فقط برای مدیر اصلی است. state machine قبلی حفظ شده است:

- `pending → cleared | bounced | canceled`
- `bounced → cleared | canceled`
- `cleared` و `canceled` نهایی‌اند.

هر رویداد همراه audit actorدار و snapshot قبل/بعد در یک transaction ذخیره می‌شود. رویداد `canceled` مقدار `is_active` را false می‌کند، اما چک و تاریخچه حذف نمی‌شوند.

### تاریخچه ممیزی

`GET /api/v1/cheques/{cheque_id}/audits` فقط برای مدیر اصلی است و رکوردهای `create`، `update`، `event` یا `legacy_snapshot` را به ترتیب زمان و شناسه برمی‌گرداند. snapshot نام کاربری و نام کامل باعث می‌شود تغییرات بعدی حساب کاربری، تاریخچه مالی را مبهم نکند.

## migration و حفاظت از داده قدیمی

migration شماره `0015_cheque_audits` جدول audit را اضافه می‌کند. برای هر چک موجود دقیقاً یک `legacy_snapshot` با actor خالی ساخته می‌شود. خود چک تغییر محتوایی نمی‌کند؛ فقط اگر `updated_at_utc` قدیمی خالی باشد، برای فراهم‌کردن token همزمانی با `created_at_utc` همان رکورد پر می‌شود.

آزمون migration از revision `0014_ledger_due_dates` یک چک قدیمی با مبلغ، وضعیت، تاریخ‌ها و یادداشت مشخص ساخت و سپس تا head ارتقا داد. نتیجه:

- `PRAGMA integrity_check = ok`؛
- مبلغ، وضعیت و سایر مشخصات چک بدون تغییر؛
- `updated_at_utc` برابر timestamp قبلی ایجاد؛
- دقیقاً یک audit با action برابر `legacy_snapshot` و actor خالی؛
- snapshot شامل اطلاعات کامل همان چک.

ارتقا روی کپی دیتابیس محلی نیز تا revision `0015_cheque_audits` با `PRAGMA integrity_check = ok` انجام شد. دیتابیس محلی در زمان آزمون چک قدیمی نداشت؛ آزمون خودکار بالا سناریوی legacy دارای چک را به‌صورت واقعی اجرا می‌کند.

## آزمون دستی پس از اتصال رابط کاربری

1. یک چک دریافتی و یک چک پرداختی ثبت کنید و timestamp و ردیف create در تاریخچه را ببینید.
2. چک pending را باز کنید، بانک/مبلغ/سررسید را تغییر دهید و دلیل بنویسید؛ مقدار قبل و بعد را در تاریخچه بررسی کنید.
3. همان فرم قدیمی را دوباره ذخیره کنید؛ پیام stale باید نمایش داده شود و تغییر دوم اعمال نشود.
4. چک را وصول، پاس، برگشت یا ابطال کنید و snapshot رویداد و نام مدیر را بررسی کنید.
5. پس از ابطال، مطمئن شوید چک در تاریخچه باقی مانده ولی قابل ویرایش نیست.
6. با حساب زیرمدیریت ایجاد، ویرایش و رویداد را امتحان کنید؛ تا فاز RBAC باید عدم مجوز نمایش داده شود.
7. موارد بالا را در عرض موبایل `390 × 844` تکرار کنید؛ دیالوگ، تاریخچه و دکمه‌ها نباید بریده یا هم‌پوشان شوند.

## تست خودکار

تست‌های backend موارد زیر را پوشش می‌دهند:

- create/update/event و audit اتمیک actorدار؛
- normalization رقم فارسی و مبلغ؛
- ویرایش موفق، no-op، stale token، تاریخ نامعتبر و شخص مفقود/غیرفعال؛
- منع ویرایش چک canceled و حفظ رکورد آن؛
- پاسخ `401` بدون نشست و `403` برای کاربر غیرمدیر؛
- ترتیب قطعی رویدادها؛
- migration واقعی و legacy snapshot بدون تغییر داده مالی.

نتیجه مجموعه کامل backend در بازبینی عامل اصلی: `185 passed` با ۶ هشدار deprecation موجود در وابستگی‌ها/کدهای قبلی. تست اعداد frontend برابر ۳ از ۳ و build production با ۹۷۶ ماژول موفق بود.
